1. Introduction					*vim9ls-introduction*

vim9ls is a language server for |Vim9| script and legacy Vim script.  It is
written in Vim9 script and runs in a Vim of its own, so it answers from what
that Vim knows: its help files, its builtin functions, options and commands,
and the plugins you already have.  A new function or option is there as soon
as Vim has it, since nothing is copied out of Vim.  Nothing else needs to be
installed.

The diagnostics are Vim's own.  The script is read with |:source-dryrun|,
which runs nothing in it and compiles its |:def| functions, so what is
reported is what Vim finds in the script, not what another parser guesses.

==============================================================================
2. Requirements					*vim9ls-requirements*

Vim 9.2.1xxx or later with the |+channel| and |+job| features.

What those patches are for:
9.2.1xxx: |getinfo()| gives the names and the types of the arguments in
          the signature help of a builtin
9.2.1084: |:source-dryrun| brings the diagnostics from Vim itself
9.2.1055: lets a function holding a lambda compile after an earlier one
          failed, which the checker relies on
9.2.1049: adds |--stdio-channel|, which is how the server talks to a client
          on stdin and stdout

The Vim that runs the server does not have to be the one that is editing, but
with lsp.vim it is: |vim9ls#Command()| names |v:progpath|.

==============================================================================
3. Installation					*vim9ls-installation*

With a plugin manager, with vim-plug for instance: >vim9

	Plug 'h-east/vim9ls'
<
Or put it under a |packages| directory as "pack/*/opt/vim9ls", which does not
load on its own, and add this to your |vimrc|: >vim9

	packadd! vim9ls
<

==============================================================================
4. Setup					*vim9ls-setup*

Any LSP client that talks stdio can use the server.  lsp.vim is the
recommended one:
	https://github.com/h-east/lsp.vim

With lsp.vim ~
Install it the same way and add an entry for "vim" files to
|g:lsp_server_list|: >
	{name: 'vim9ls', filetypes: ['vim'], cmd: function('vim9ls#Command')}
lsp.vim calls the Funcref when the server starts, so vim9ls does not have to
be in 'runtimepath' yet when the vimrc is read.

						*vim9ls#Command()*
vim9ls#Command() returns the command that starts the server with the Vim it is
called in.  On MS-Windows it names vim.exe when called from gvim.exe, so that
no window opens.  It throws when that Vim lacks |+channel| or |+job|, or is
older than 9.2.1xxx.

With another LSP client ~
Point the client at bin/vim9ls (bin/vim9ls.cmd on MS-Windows), a script that
starts the server with "vim" from $PATH.  $VIM9LS_VIM names another Vim.  What
it runs is >
	vim --clean --stdio-channel -S /path/to/autoload/vim9ls.vim
and the server talks to the client on stdin and stdout, which every client
supports.  See |--stdio-channel|.

5. What it does					*vim9ls-features*

Positions are counted the way the client asks for at initialize: "utf-8"
when it offers that, which needs no conversion, "utf-16" otherwise.

Hover ~
The help entry for the builtin function, option, Ex command or "v:" variable
under the cursor, as Vim's help has it.  An option is recognized after "&" and
in a ":set" command, a command at the start of a statement.  Variables and
functions of the script itself have no help and give nothing.
This is for editors other than Vim.  In Vim, |K| opens the same entry in a
help window, which is the better place to read it.

Completion ~
Builtin functions, plus the functions, variables, classes and other names the
script defines.  After "&" and in a ":set" command: options.  At the start of
a statement: Ex commands as well.  "v:" variables after "v:".
After a ".": the exported names of the imported script when the name before
it is the alias of an import, the members of a class or an enum when it is
their name, of the class a variable is declared with or made with
"Class.new()", and of the class around "this".  After "foo#bar#": the
functions of autoload/foo/bar.vim and the files below it as "foo#bar#name#".
The help entry of a builtin comes with "completionItem/resolve", for the item
the client asks about: its first line as the detail, the rest as the
documentation.

Document symbols ~
The functions, variables, constants, classes with their members, enums with
their values, interfaces, augroups, imports and user commands of the script,
nested the way they are written.  Legacy "function" and Vim9 "def" both count.

Definition, references and rename ~
For the names the script defines: functions, variables and parameters, classes
and their members, enum values, imports and user commands.  A name is looked
up from where it is used: the innermost function that declares it wins, so a
local hides a script variable of the same name.  A member counts only after a
".", and a function named in a string ("function('Name')") counts as a use; a
variable named in a string does not.
Under Vim9 rules "s:Name" and "Name" are the same script-local name; in legacy
script they are two different functions.
Definition also follows an import: "alias.Name" goes to the exported name in
the imported script, and the alias itself to that file.  A relative import is
found next to the script, an autoload import in the autoload directories above
it and in $VIMRUNTIME.  A legacy "foo#bar#Func()" goes to autoload/foo/bar.vim
the same way.
References and rename follow an exported name and a legacy autoload function
into the other scripts: those of the plugin the defining script belongs to,
which is the directory above its autoload, plugin, ftplugin, import, syntax
or indent directory, and the open documents.  A use is the name after the
alias of an import of that script, or the autoload name "foo#bar#Func" spelled
out, also in a string.  Scripts elsewhere on 'runtimepath', and a name put
together at runtime, are not found.
Rename changes the name proper and leaves a "s:" or "<SID>", or the "foo#bar#"
of an autoload name, in place.  A name that is not defined in the document
and not shared by the script that defines it, a builtin for one, cannot be
renamed.
Under Vim9 rules a variable declared inside a block, an "if", "while", "for"
or "try" with each of its branches, is seen from its declaration to the end
of that block, so two blocks may declare the same name and are told apart.
A block of its own, "{" to "}", is not told apart from what holds it.

Document highlight marks the other uses of the name in the document alone,
which is what an editor colors in the buffer it has open.  A declaration and
an assignment ("x = 1", "x += 1") are reported as a write, everything else as
a read.  A builtin function or a "v:" variable is marked by name, since the
parser does not track what Vim itself defines.

Signature help ~
Inside a call, the signature of the function with the argument the cursor is
in marked: for a builtin the first line of its help entry, with the rest of
the entry as documentation, for a function of the script or an imported one
its "def" or "function" line.  After "->" the value in front counts as the
first argument.  A call that started up to 30 lines above the cursor is found.
With a Vim that has |getinfo()| the signature of a builtin is built from
what that reports: the names of the arguments, how many there are and which
are optional, the types each accepts, "{expr}: string | list<any>", the
return type after the ")", and the argument the value before "->" fills,
which for append() is the second.  An argument Vim does not name, the second
of getreg(), or that accepts several types and is named after one of them,
"{list}" of get(), is shown as "{argN}", N being its number.

Inlay hints ~
The type of a "var" that leaves it to the initializer, shown after the name
as the Vim9 compiler infers it: from the literals, operators, indexing and
lambdas of the initializer, the declared types of the variables and
parameters in scope, the "def" lines of the script's functions, and for a
builtin what |getinfo()| reports; without that function a builtin gives
no type.  An initializer that goes on over lines is read to its end.  A type
that cannot be told gives no hint.
And the name of the parameter in front of each argument of a call, "start:",
from what signature help knows: the help entry of a builtin, the definition
of a function of the script.  The argument the value before "->" fills gets
none, nor does one that is the name itself, nor one signature help would
show as "{argN}", nor one of a builtin named after its type, "{string}" of
strlen().

Code actions ~
A quick fix for what the parser reports, offered for the diagnostics in the
range asked about: ":let" under Vim9 rules becomes "var" when it declares the
variable and goes when the variable is there already or has a scope; the end
a block lacks, "endif" for one, is put in where the indentation of the block
stops; an end without a start is removed.

Diagnostics ~
Reported when a document is opened and after its changes pause:
- a block that is not closed ("if" without "endif", "def" without "enddef",
  and so on) and an end without a start, with the error Vim would give;
- ":let" where Vim9 rules apply, in a |vim9script| file or inside a ":def";
- in legacy script, a word at the start of a statement that is not a command,
  as a warning; an assignment, a call or a user command does not count.  Under
  Vim9 rules a statement may start with any expression, so nothing is reported
  there;
- a call of a function that is not defined: a builtin Vim does not have, a
  script-local function the script does not define, a legacy autoload function
  its file does not have, and under Vim9 rules a name the script does not
  define.  A global function may be defined anywhere and is left alone, and so
  is a call in a pattern, in keys or in the value of an option;
- a "v:" variable Vim does not have.
The reading is line by line and does not run the script.

At the same time Vim itself reads the document.  The checker, a Vim of its
own that the server starts once and keeps, sources the text under the file's
own name, so that a relative import is found, with |:source-dryrun|: what
the script defines is defined, nothing in it runs, and every ":def" is
compiled.  In a |vim9script| file the script level goes along once more as
the body of a function, so that it is compiled as well; a declaration is
checked against its type.  A user command there is left out, the checker's
Vim loads no plugins and would not know it.  The server does not wait for
the checker, it goes on answering the client and sends the diagnostics once
the checker has answered.  What Vim reports is added, each on the line it is
about: a type mismatch, a name that is not found, an argument too many.
What a legacy "function" does is not read until it is called, and neither is
a mapping or an autocommand.  A Vim without |:source-dryrun| leaves this out.

==============================================================================
6. Environment					*vim9ls-environment*

$VIM9LS_LOG	When set, the server appends its channel log to this file.
		See |ch_logfile()|.  Requests, responses and the errors the
		server ran into end up there.

$VIM9LS_VIM	The Vim that bin/vim9ls starts.  Default: "vim" from $PATH.

==============================================================================
7. Development					*vim9ls-development*

The tests are in test/ and run with: >
	cd test && ./run
	VIMPROG=/path/to/vim ./run
	TEST_FILTER=hover ./run
The Vim they run in is also the server they start, so it needs
|--stdio-channel|; without |:source-dryrun| the test of the checker is
skipped.  Unit tests read the parser and the conversions directly; the server
tests start the server and talk LSP to it.
